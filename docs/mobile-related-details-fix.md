# 移动端当前单据明细阻塞复核

## 结论与证据

反馈来自 Linux 客户端，但未提供具体客户端版本、诊断编号或原工程。当前代码中可以确认的能力缺口是：桌面 `Table` 已有 `sourceForeignKey`，移动端 `MTaskList` / `MFeedList` 原先只有普通过滤，没有等价的当前来源行关联读取能力。旧契约下反复重试生成，无法为这两种移动物料增加宿主能力。

`待绑定引用表` 来自 `reviewPageDependencies`：指定来源表、来源列、明细表和外键结构通过检查后，目标页没有绑定依赖中的明细表。它不是 JavaScript 崩溃，也不等于引擎已经验证了当前单据的明细隔离。模型回复只能作为排查线索，不能单凭回复认定用户工程中的所有问题。

回归夹具使用真实 `projectContext` 和 MCP `callTool`，复现完整诊断：

```
oa-m-approvals ← oa-pc-expenses · 查看当前报销明细（待绑定引用表）
```

原候选只显示“明细尚未接入”。添加支持的明细列表后，一次 `protoflow_apply_tsx_patch` 即可得到 `acceptanceReady=true`，宿主准备提交时只改变目标页，表、记录及来源页面保持不变。这是同类场景的确定性复现，不是对尚未取得的用户原工程的复现。

## 修复

- 两种移动列表支持 `table + sourceForeignKey`。`table` 是工程表 ID，`sourceForeignKey` 是明细表的物理外键字段名；通过真实外键引用定位来源列，不猜测主键叫 `id`，不用列 ID 代替字段名。
- 来源可以是列表行事件打开弹层时的行，或 `navigate(目标页面ID,"row")` 带入的行。记录按原始值和类型精确匹配，数值 `0` 有效且不等于字符串 `"0"`。
- 来源缺失、不匹配、外键无效时不会返回全量明细。普通过滤只在已隔离的数据中继续缩小范围。
- 桌面表格与移动列表共用来源读取逻辑；暂存预览中的来源数据具有权威性，不会退回正式数据寻找来源记录。
- 更新物料元数据、AI 生成规则、实现指南、渲染诊断、宿主/MCP 契约和发布快照校验。保留原有验收要求，不把“未接入”提示当作完成，也未把所有普通外键依赖强行解释为明细隔离。
